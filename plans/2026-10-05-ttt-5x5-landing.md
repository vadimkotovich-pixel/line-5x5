# Plan — «Линия 5×5» (2026-10-05)

Режим bulletproof: **M** (новая фича, 6 файлов кода + тесты). Стадии: research → spec → plan →
фазы 1–4 (каждая с self-audit/verification/impact) → интеграционная проверка → ревью → финал.

## Challenge Log (обязательный перед стартом)

**1. Решает ли план проблему?** Все AC покрыты: AC1–AC7 — фаза 1 (`rules.js`), AC8–AC11 — фаза 2
(`ai.js`), AC12 — фаза 4 (контракт-тест), AC13 + визуал — фазы 3–4 и финальная проверка владельцем.
Непокрытых критериев нет.

**2. Это самое эффективное решение?** Альтернативы:
- *React/Vite + компонент поля.* Плюсы: привычно. Минусы: сборка, `node_modules`, страница не работает по
  `file://` без билда. Для одной страницы — лишняя инфраструктура. Отвергнуто.
- *Один HTML-файл со всем инлайном.* Плюсы: один файл. Минусы: логику нельзя юнит-тестировать без
  извлечения кода из разметки, CSS/JS не переиспользуются. Отвергнуто.
- *ES-модули + локальный сервер.* Плюсы: современно. Минусы: `file://` ломается по CORS, нужен сервер.
  Отвергнуто.
- **Выбрано:** `index.html` + `styles.css` + три classic-скрипта с UMD-оберткой. Ноль зависимостей,
  работает двойным щелчком, логика тестируется в Node. Лучшее соотношение «результат / сложность».

**3. Нет ли «кода ради кода»?** Каждый файл обслуживает AC. Отброшено: уровни сложности бота (вне scope),
сохранение партий в localStorage (вне scope), минимакс (не нужен для «среднего»), шрифты/иконки из CDN
(офлайн-работа важнее). Счётчик серии партий оставлен — прямо обслуживает задачу лэндинга (удержание).

## Архитектура

```
ttt-5x5-landing/
├── index.html                     # разметка лэндинга + контейнер игры
├── assets/css/styles.css          # тёмная тема, адаптив, анимации
├── assets/js/rules.js             # AC1-AC7: окна, подсчет, блокировки, конец партии
├── assets/js/ai.js                # AC8-AC11: 1-ply эвристика с защитой
├── assets/js/ui.js                # DOM, события, клавиатура, анимации
└── tests/{rules,ai,ui-contract}.test.js
```

Контракты:
- `Rules.createGame() -> State`; `Rules.applyMove(state, index, player) -> State` (иммутабельно);
  `Rules.evaluateMove(state, index, player) -> {points, lines, blockedCells}`;
  `Rules.canPlay`, `Rules.emptyCells`, `Rules.hasPotential`, `Rules.result`, `Rules.LINES`, `Rules.linesThrough`.
- `AI.chooseMove(state, player) -> index | null`.
- `State = {size, cells[25], blocked[25], scores{X,O}, turn, status, lastMove, moves}`.

## Фазы

### Фаза 1 — `rules.js` (TDD)
Тесты: 48 окон; тройки в 4 направлениях; `L−2` очков; блокировка клеток; заблокированная клетка
недоступна навсегда; конец партии по заполнению и по отсутствию потенциальных троек; определение
победителя; иммутабельность. Затем реализация. Гейт: `node --test tests/rules.test.js`.

### Фаза 2 — `ai.js` (TDD)
Тесты: забирает свое очко; блокирует чужую тройку; предпочитает 2 очка 1 очку; не отдает 2 очка за 1;
легальность хода и завершаемость на 300 партиях (бот-против-бота и бот-против-случайного); независимая
перепроверка очков полным сканированием поля. Гейт: `node --test tests/ai.test.js`.

### Фаза 3 — `index.html` + `styles.css`
Секции: шапка → hero с игрой → правила с мини-схемами → таблица очков → «как обыграть компьютер» → футер.
Мини-схемы рисуются той же сеточной разметкой, что и поле. Адаптив, тёмная тема, `prefers-reduced-motion`.
Гейт: наличие всех `id`, на которые ссылается `ui.js`.

### Фаза 4 — `ui.js` + контракт-тест
Рендер, клики, ротация `tabindex` + стрелки/Enter, `aria-live` статус, подсветка зачеркнутой линии,
блокировка ввода на время «хода» бота, оверлей результата, счёт серии партий. Гейт: контракт-тест +
`node --check` + полный `node --test`.

## Риски и как закрываем

| Риск | Митигация |
|---|---|
| Бот «обменивает 1 на 2» и выглядит глупо | оценка хода включает лучший ответ соперника (вес 900 против 1000) + отдельный тест AC10 |
| Иммутабельность нарушена → просмотр ломает партию | `applyMove` клонирует состояние; тест «вход не изменен» |
| Рассинхрон UI и логики | контракт-тест: множество требуемых `id` ⊆ множество `id` в HTML |
| Страница не открывается по `file://` | никаких ES-модулей, classic-скрипты |
| Бессмысленные клики в конце партии | детект «троек больше не будет» (`hasPotential`) закрывает партию |
| Визуальная проверка невозможна в песочнице | честно сообщить владельцу, дать путь файла и команду для скриншота |

## Проверка (Gates)

1. `node --check` по трем скриптам — 0 синтаксических ошибок.
2. `node --test --test-isolation=none tests/…` — 46 тестов зелёные.
3. Инварианты self-play: 300 партий, все завершаются, нет клеток «одновременно занята и заблокирована»,
   нет повторного использования заблокированной клетки, очки независимо перепроверены.
4. Контракт UI↔HTML.
5. Вёрстка в настоящем браузере: скриншоты + `overflow=0` на 1422 и 380 CSS px.
6. Финальный отчёт: что проверено инструментами, что осталось на визуальный осмотр владельца.

## Corrections — что выяснилось по ходу работы

План переписывался по фактам, а не подгонялся под результат. Что изменилось:

1. **Формула оценки бота.** В плане и research было `1000·свои − 900·ответ`. При таком весе
   позиционная оценка (до 94) могла перевесить настоящее очко (разница 100) и бот иногда отказывался
   бы брать свою линию. Заменено на эквивалент по смыслу, но без зазора:
   `1000·(свои − ответ) + позиция`, где позиция строго меньше 1000. Теперь порядок величин
   «очко важнее позиции» гарантирован арифметикой, а не подбором весов.
2. **Тесты важнее моих выкладок.** Тест числа окон через клетку (0,1) сначала «падал правильно»:
   я посчитал 3 окна, реализация сказала 4 — клетка может не только продолжать окно, но и начинать
   его. Исправлено ожидание, а не реализация; независимая проверка — ровно 48 окон (15+15+9+9).
3. **Проверка «символ остался в клетке» неверна для засчитанного хода.** Если ход закрывает линию,
   символ сразу снимается в зачеркнутую клетку. DOM-тест поймал это на реальной партии.
4. **jsdom добавлен как dev-зависимость.** План предполагал только контракт-тест UI. Этого мало:
   контракт не проверяет runtime. Появился `tests/dom.test.js`, который играет партию кликами
   в настоящем DOM и сверяет интерфейс с правилами. Страница при этом остаётся без зависимостей.
5. **Среда диктует команды.** `node --test` по умолчанию спавнит процессы (в песочнице EPERM),
   поэтому нужен `--test-isolation=none`; junction-ссылки pnpm в песочнице не разворачиваются,
   поэтому установка через `--node-linker=hoisted`.
6. **Ловушка кодировки.** PowerShell-раундтрип превратил русский текст копии страницы в нечитаемые
   пары латинских букв с диакритикой, и первые скриншоты проверяли испорченный файл. Теперь: генерация
   харнессов только через Node, плюс тест-сторож на BOM и двойную перекодировку (он же запретил
   цитировать испорченный текст даже в документации). Сам `index.html` был чист всё время.
7. **«Мобильный» скриншот оказался артефактом.** Headless Chrome на Windows не делает окно уже ~500 px:
   при `--window-size=400` реальный `clientWidth` = 504, а картинка обрезалась до 400 — выглядело как
   поломка вёрстки. Настоящее переполнение измерено: `overflow=0`. Узкая вёрстка проверена
   через iframe 380 px.
8. **Строка «Крест» в таблице очков** была невнятной текстовой пометкой; заменена на мини-схему креста,
   которая рисуется тем же кодом, что и остальные схемы. На узких экранах таблица и список фактов получили
   отдельные правила (`≤560px`, `≤480px`), иначе колонка «Линия» сжималась до нечитаемой.
9. **Кодировка и среда — часть контракта.** В `tests/ui-contract.test.js` добавлен тест на UTF-8
   без BOM для всех текстовых файлов проекта.

Отброшено как «код ради кода»: уровни сложности бота, сохранение партий, минимакс, анимация
пересылки знака, отдельный сервер для локального просмотра.
